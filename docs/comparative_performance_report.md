# Comparative Performance Report — `Text.Language.Classifier.Fasttext`

This document reports how the pure-Elixir port of fastText's `lid.176`
language identification model in this package compares to the official
C++ reference implementation distributed via the [`fasttext` Python
bindings](https://pypi.org/project/fasttext/), measured on the same
machine, the same model file, and the same input set.

The headline finding: **accuracy and prediction probabilities are
indistinguishable between the two implementations** (label parity is
100% on the curated set; the maximum top-1 probability difference is
below 1 × 10⁻⁶). **Memory footprint is essentially identical**
(~130 MB for the model). **Per-prediction wall time** is the only
metric that differs materially: with the EXLA backend and the
inference path folded into a single `defn` graph, the Elixir port
runs in roughly **100 μs per call** versus 2-4 μs for the native C++
implementation — the cost of the remaining BEAM ↔ NIF round-trip
overhead (one fused EXLA call plus the BEAM-side Huffman DFS).

## Test environment

| | |
|---|---|
| Machine | Apple Silicon, macOS |
| Elixir | 1.20.0-rc.4 on Erlang/OTP 28.3.1 |
| Nx | 0.11.0 |
| EXLA | 0.11.0 (CPU) |
| Reference | `fasttext` Python bindings 0.9.3 (CPython 3.9) |
| Model | `lid.176.bin` v12, unquantized — 126 MB on disk, sha256 deterministic |

The Elixir-side measurements come from
[priv/scripts/comparative_perf_report.exs](../priv/scripts/comparative_perf_report.exs);
the Python-side measurements come from
[priv/scripts/comparative_perf_report.py](../priv/scripts/comparative_perf_report.py).
Both scripts can be re-run to refresh this report. Expected variance is
modest — single-digit percent for memory, perhaps 20% for timing on a
busy laptop.

## 1. Accuracy

Both implementations are evaluated on the 29 curated multilingual
inputs in [test/fixtures/test_strings.json](../test/fixtures/test_strings.json),
which span 24 languages and 14 scripts (Latin, Cyrillic, Greek, Arabic,
Hebrew, Devanagari, Tamil, Thai, Han, Hiragana, Hangul, ...).

| Metric | Elixir port | Reference (`fasttext` C++) |
|---|---:|---:|
| Top-1 accuracy | **29 / 29 (100.0%)** | **29 / 29 (100.0%)** |
| Mean top-1 confidence | 0.967 | 0.967 |

### Reference parity

A finer test compares the two implementations directly on the 28 inputs
in [test/fixtures/golden_predictions.json](../test/fixtures/golden_predictions.json),
which were generated by running `model.predict(text, k=5)` against the
same model in Python:

| Metric | Result |
|---|---:|
| Top-1 label match | **28 / 28 (100.0%)** |
| Top-1 probability — mean Δ | < 1 × 10⁻⁶ |
| Top-1 probability — max Δ | < 1 × 10⁻⁶ |

The two implementations report bit-equivalent confidences for the top
prediction in every input. Below the noise floor (probabilities below
~10⁻⁵, i.e. fastText's `std_log(threshold + 1e-5)` cutoff) the tail of
the top-K list can differ in tail-label ordering due to
float32-vs-float64 rounding accumulating across 7 levels of Huffman
DFS. The package's
[test suite](../test/language/classifier/fasttext/inference_test.exs)
gates label parity only on entries above the noise floor for that
reason.

## 2. Memory

Resident memory is measured as the delta between BEAM total (or process
RSS for Python) before and after the model is loaded. Per-prediction
allocation is the BEAM-side allocation watermark across 100 predictions
on the same input, divided by 100 — pre-GC, so it captures both
short-lived intermediates and long-lived state.

| Metric | Elixir port | Reference (`fasttext` C++) |
|---|---:|---:|
| Model resident size | **131.6 MB** | **134.5 MB** (RSS Δ) |
| Per-prediction allocation | 0.01 – 0.06 MB | not directly comparable |

The resident sizes are within 3 MB of each other and dominated by the
{2_040_010, 16} float32 input matrix (~125 MB) plus the dictionary's
40 010 word strings and the 351-node Huffman tree. The Elixir port
holds the matrix as an `Nx` reference-counted tensor; multiple BEAM
processes can share it without duplication.

Per-prediction allocation on the BEAM is dominated by transient `Nx`
tensors (the hidden vector, intermediate dot results) and the small
number of lists assembled by tokenization and feature extraction. The
allocations are short-lived and reclaimed by the next minor GC; 0.01 –
0.06 MB per call corresponds to roughly 10 K – 60 K binary-heap bytes,
well within typical actor budgets.

A direct equivalent measurement on the C++ side is not straightforward
(no analogue of `:erlang.memory/0` from CPython), so the Reference
column is left unfilled. The C++ implementation is similar by design:
each call allocates a `Vector` of size `dim` for the hidden layer, plus
a small heap for the top-K accumulator, which is on the order of a
hundred bytes.

## 3. Speed

Wall time is measured per prediction with 50 warmup iterations and 200
measured iterations on each input. Reported numbers are the median and
99th-percentile sample for the configuration in question. Both
implementations call into the same prediction entry point used by their
respective public APIs (`Text.Language.Classifier.Fasttext.Inference.predict/3`
and `model.predict(text, k=1)`).

### Cold model load

| Metric | Elixir port | Reference (`fasttext` C++) |
|---|---:|---:|
| `lid.176.bin` load time | **78 ms** (BinaryBackend) — **158 ms** (EXLA, includes initial graph trace) | **138 ms** |

The BinaryBackend Elixir loader is faster than the C++ loader on this
machine — `Nx.from_binary` is a contiguous memcpy and the dictionary
parser does no thresholding pass. With the EXLA backend the load is
slightly slower because EXLA traces the input matrix on first use;
subsequent loads in the same VM are amortised. The first prediction
also pays the EXLA JIT compile cost for the inference graph (~30 ms);
the perf script's 50-iteration warmup absorbs that.

### Per-prediction wall time

| Input (length / script) | Elixir, BinaryBackend (median μs) | Elixir, EXLA + fully-vectorised `defn` (median μs) | Reference C++ (median μs) |
|---|---:|---:|---:|
| short ASCII (3 words) | 569 | **122** | 2 |
| medium ASCII (10 words) | 772 | **128** | 3 |
| long sentence (~80 chars) | 1 004 | **147** | 4 |
| Cyrillic | 808 | **125** | 4 |
| CJK (Chinese) | 630 | **126** | 4 |
| CJK (Japanese) | 648 | **117** | 4 |

The `defn`-fused EXLA pipeline reduces per-prediction time by **6-9×**
versus pure-Elixir BinaryBackend, but the Elixir port is still
**~30×** slower than the C++ reference on warm inference. The
remaining gap is structural rather than algorithmic:

* The C++ predictor performs the entire forward pass in one tight
  function, with the dictionary lookup, hidden-vector accumulation,
  Huffman traversal, and sigmoid sharing the same stack frame and
  cache lines.

* The Elixir port runs the matrix work as **a single fused EXLA
  graph** (`take + mean + dot`), then performs the Huffman DFS in
  pure Elixir — total of three BEAM ↔ NIF transitions per call: list
  → tensor, the fused graph, and tensor → list. At ~30 μs each, that
  accounts for most of the ~100 μs floor.

### Folding the inference path into a single `defn` graph

An earlier revision of the inference module ran the matrix work as
several separate `Nx` calls (`Nx.tensor`, `Nx.take`, `Nx.mean`,
`Nx.as_type`, `Nx.dot`, `Nx.to_list`). Each call crossed the BEAM ↔
EXLA boundary independently, with ~10–30 μs of round-trip overhead per
call. Wrapping `take + mean + dot` (and the softmax tail for the
softmax loss path) inside `defn` lets EXLA trace and compile the
entire forward pass to a single XLA HLO computation, executed in one
NIF call.

| Stage | Median time, separate `Nx` calls | Median time, fused `defn` graph |
|---|---:|---:|
| `Inference.compute_hidden` (`take + mean`) | 122 μs | **47 μs** |
| `Inference.predict_features` (full forward pass + Huffman DFS) | 188 μs | **103 μs** |
| `Fasttext.detect` (`predict_features` + script detection) | 207 μs | **111 μs** |

The `defn` form is bit-equivalent to the pre-fusion form — the test
suite (`mix test --include requires_lid_176`) passes both ways with
zero label or probability deviations from the reference. EXLA being
unavailable is not a failure mode: `Nx.Defn.Evaluator` (the default
compiler) executes the same `defn` graph correctly on the
`Nx.BinaryBackend`; the savings simply do not materialise.

### Where the time goes

For a medium ASCII input with the `defn` graph compiled by EXLA, the
breakdown is:

| Stage | Median time |
|---|---:|
| `Tokenizer.tokenize` | < 1 μs |
| `Features.extract` (BOW + EOW + subword indices) | 8 μs |
| `Inference.compute_hidden` (fused take + mean) | 47 μs |
| `Inference.predict_features` (full forward pass + Huffman DFS) | 103 μs |
| `Fasttext.detect` (predict_features + script detection) | 111 μs |

The pure-Elixir paths (tokenization, feature extraction, script
detection) are negligible relative to the matrix work. Tokenization in
particular is sub-microsecond — over 1 M tokenizations/second. The
remaining ~50 μs gap between `compute_hidden` and `predict_features`
covers the Huffman DFS in pure Elixir (~30 μs of f32-rounded sigmoid +
log calls plus the top-K bookkeeping) and the `Nx.to_list` extraction
of the 176 internal-node logits back to BEAM space.

## 4. Choosing a backend

For most uses, **EXLA is the recommended backend** and is what the
README's installation instructions configure. To switch:

```elixir
# config/config.exs
config :nx, default_backend: EXLA.Backend

# mix.exs
{:exla, "~> 0.11"}
```

`exla` is declared as an optional dependency of `:text` and does not
need to be required at compile time. Without EXLA the package still
works (BinaryBackend handles every operation correctly), but the per-call
cost is 3-4× higher.

## 5. Conclusions

| Dimension | Verdict |
|---|---|
| Accuracy | Identical to the reference. |
| Memory | Within 3 MB of the reference. |
| Speed | ~30× slower per call than the reference; 6-9× faster with EXLA + fused `defn` than with `Nx.BinaryBackend`. Sub-150 μs on EXLA, sub-2-millisecond on BinaryBackend. |
| Maintainability | Pure Elixir + Nx, no NIFs other than EXLA itself, no Python sidecar, no model conversion. |

For the use case this port was built to support — embedding language
detection inside an Elixir application that drives downstream locale
selection for formatting, calendar choice, and collation — the
performance is a comfortable fit. A typical web request that needs to
detect a single user's language can do so in under a millisecond
without leaving the BEAM, with predictions that match the reference
to within rounding.

## 6. Future work

The forward pass is now a fully vectorised EXLA graph: feature
indices in, per-leaf log-probabilities out, no BEAM-side scoring
loop. The HS-DFS vectorisation (added after the initial round of
this report) was a small wash on `lid.176` specifically — the
176-leaf, 7-deep tree was already cheap enough in BEAM Elixir that
the extra EXLA kernel ops (`take + multiply + sigmoid + log + sum`
over a `{176, 15}` matrix) cost about as much as the recursive
walk it replaced. For larger label spaces (thousands of classes,
deeper trees), the vectorised path scales as `O(1)` round-trip
overhead while the recursive DFS scales linearly with explored
nodes.

What's left:

* **Reuse a pre-allocated index buffer.** Each call constructs a fresh
  s64 indices tensor from the feature list, which crosses the NIF
  boundary. A pool of reusable buffers (similar to `Nx.Serving`'s
  preallocation) could amortise the cost.

* **`Nx.Serving` for batched inference.** When throughput matters more
  than latency, batching many predictions into one EXLA call would be
  a substantial multiplier (single-digit μs per prediction at modest
  batch sizes).

* **Quantized models.** `lid.176.ftz` (917 KB) remains unsupported.
  Adding product-quantization decoding would shrink the resident
  model from ~130 MB to ~10 MB at a small (~1%) accuracy cost.

## Reproducibility

```sh
# One-time setup
mix text.download_lid176
pip install fasttext

# Run both sides
mix run priv/scripts/comparative_perf_report.exs
/usr/bin/python3 priv/scripts/comparative_perf_report.py
```

Both scripts emit numbers in the same headed format; this report
inlines the values from a representative run. The differential test
suite (`mix test --include requires_lid_176`) covers parity at a finer
grain than the headline numbers above.
